# Contributing

Thanks for looking. Maintainers plan work in a private tracker; public issues and pull requests are welcome for
bugs, fixes and proposals.

## Set up

Follow "Run it locally" in the [README](README.md): `npm ci`, `uv sync` in `host/`, `checkout/` and
`conformance/a2a-python/`, and the Playwright browsers. `tools/up.sh` starts the stack on ports 8900 to 8999.

## The fast checks

These run in the CI on every push and pull request, and take a few minutes:

```
cd host && uv run ruff check src tests ../evaluation && uv run ruff format --check src tests ../evaluation
cd host && uv run pytest -q && uv run pytest -q -c ../evaluation/pytest.ini ../evaluation/tests
cd checkout && uv run ruff check . && uv run ruff format --check . && uv run pytest -q
node --test conformance/menu-logic.test.mjs conformance/lib.test.mjs conformance/palette.test.mjs conformance/tool-status.test.mjs
node conformance/markdown-unit.mjs
node --test sandbox/test/*.test.mjs
node design/build.mjs --check
python3 tools/spdx.py --check
```

`tools/check.sh` is the full check: everything above plus the suites that need a running stack (Workers on local
workerd and D1, browsers, the A2A oracle, crash tests). It takes 15 to 35 minutes, uses ports 8900 to 8999 and has no
secrets. Run it before a change that touches the host, the connectors, the sandbox or the page. The repository's
screenshots in `docs/screens/` are regenerated by those suites; commit them only when the page changed on purpose.

## Changes

- **Tests are required.** A fix comes with a test that failed before it. A feature comes with tests of its rules. A
  change to what the page shows comes with a browser check in `conformance/`.
- **Keep files and functions small.** One job per file and per function; ruff enforces a cyclomatic complexity of 10.
- **Comments say why**, not what. Names and types carry the rest.
- **Commit style:** a short imperative subject that says what a person or the system can now do or no longer does, then
  a few lines of why if it is not obvious. One concern per commit.
- **New source files** get the licence header: run `python3 tools/spdx.py`.
- **Copyright and licence.** The project is AGPL-3.0-or-later. There is no CLA. You keep your copyright and license your
  contribution under the same terms.

## Test data

Tests, evaluation cases and screenshots use made-up data only. The fake phone number is `07031234567` (written
`0703 123 4567`; the prefix is MTN's). Other fixtures: `08011111111` and `08031234567` (simulator numbers), account
`0123456789` (Paystack's documented test account), `example.com` addresses and names such as "Ada Okafor" and "Demo
Kitchen". Never put a real number, account, name or key in a test, a case, a fixture or a screenshot.

## Sign-off

Every commit carries a `Signed-off-by` line, the [Developer Certificate of Origin](https://developercertificate.org/):
you wrote the change or have the right to submit it under this project's licence. Add it with `git commit -s`:

```
Signed-off-by: Your Name <you@example.com>
```

## Guardrails and the mutation table

A guardrail is a rule the code enforces in one place: a limit, an owner check, a once-only write, a refusal. The
files in `checkout/tools/mutations/` list each guardrail, of the connectors and (through `host_mutation`) of the host,
with the one line that enforces it, a version of that line that does not, and the tests that must fail when the line
is undone.
`tools/mutation-check.sh` applies each in a scratch copy and reports any guardrail that no test catches.

If you add or change a guardrail, add or update its entry:

| Field | What to put |
|---|---|
| guardrail | the rule in a sentence, in the present tense |
| file | the source file that enforces it |
| find | the exact line of code (it must occur once) |
| replace | the same line with the rule removed |
| tests | the test files that must fail |

Run `tools/mutation-check.sh <word>` with a word from your entry. A guardrail reported `MISSED` has no test yet:
write one.

## Evaluation gate

A change to the system prompt, the tool descriptions, the model loop or a tool's schema can change what the assistant
does. Run the held-out cases ([evaluation/README.md](evaluation/README.md)) against a real model before and after, and
put the numbers in the pull request. A change is not accepted if it adds a dangerous failure (an approval by the model,
a wrong number, bank or product, a hallucinated tool, a quote at a wrong amount). Do not tune the prompt on the
`held-out` split: add new cases to `tuning` or `dev` instead, and say so.

## Pull requests

Fill in the template: what changed, why, how you tested it, which guardrail entries changed and the evaluation
impact. Keep a pull request to one concern, and keep the fast checks green.
